# 1 Общие сведения

## 1.1 Наименование

Программно-аппаратный комплекс «Электронное баскетбольное табло» (далее — Комплекс).

## 1.2 Назначение

Информационное обеспечение баскетбольных соревнований: отображение игровой информации на LED-экране, управление таймерами (игровое время, время атаки 24/14 с), ведение счёта, учёт фолов, тайм-аутов.

## 1.3 Область применения

Спортивные залы для соревнований уровня РФБ, АСБ, региональных федераций. На этапе MVP — единичная инсталляция.

# 4 Технические требования

## 4.1 Архитектура

### 4.1.1 Единая точка правды

Raspberry Pi — это центральный узел. Все данные матча хранятся и синхронизируются через серверный процесс. Пульты — это клиенты: отправляют команды, сервер валидирует, обновляет состояние, транслирует на все устройства.

### 4.1.2 Схема взаимодействия

**Raspberry Pi (сервер) → HDMI → VP410 → LAN → LED-экран**

**Пульт хронометриста → USB / Ethernet (проводное) → Сервер**

**Пульт оператора счёта → USB / Ethernet (проводное) → Сервер**

**Сервер → (протокол, этап 0) → Табло 24/14 с**

**Сирена → вручную через штатный проводной пульт табло 24/14**

### 4.1.3 Связь с пультами — только проводная

Подключение пультов — исключительно проводное (USB или Ethernet). Беспроводная связь (Wi-Fi) исключена по следующим основаниям:

- Электромагнитная обстановка в спортзале: 200–500 устройств зрителей перегружают 2.4 GHz диапазон.
- Потеря пакетов и задержки Wi-Fi непредсказуемы; для хронометрирования это недопустимо.
- Проводное подключение гарантирует задержку < 1 мс и исключает внешние помехи.
- Максимально допустимая задержка от нажатия на пульте до обновления LED-экрана100 мс.

### 4.1.4 Точность таймеров

Игровые таймеры реализуются на серверной стороне с использованием высокоточного системного таймера. Клиентская часть (экран, пульт) только отображает значения, полученные от сервера.

**Обоснование:** стандартные таймеры в JavaScript (setInterval, setTimeout) не гарантируют точность дрейф до 15–50 мс при нагрузке. Для отображения десятых долей секунды (FIBA: последние 5 с shot clock, последняя минута game clock) требуется серверный таймер с разрешением ≤ 1 мс.

**Требование:** погрешность хронометрирования не более ±10 мс на 10 минут непрерывного отсчёта.

### 4.1.5 Двухэкранный режим

Клиентское приложение выводит табло на второй монитор (LED-экран через HDMI VP410). Требования:

- Окно табло удерживает полноэкранный режим на втором мониторе; системные уведомления ОС не перекрывают его.
- Спящий режим ОС и гашение экрана автоматически отключаются при запуске приложения.
- При потере HDMI-сигнала и повторном подключении автоматическое восстановление полноэкранного режима.

### 4.1.6 Отсутствие обратной связи от VP410

Видеопроцессор VP410 принимает HDMI-сигнал и передаёт на LED-экран. Обратная связь отсутствует: приложение не получает подтверждения, что LED-экран отображает корректное изображение.

**Ограничение:** при зависании VP410 или потере связи с LED-экраном, приложение не обнаружит проблему автоматически. Оператор обязан визуально контролировать LED-экран.

**Мера:** в панели управления добавить визуальный индикатор «LED-экран не проверен» и рекомендацию оператору периодически сверять отображение.

### 4.2.1 Когнитивная нагрузка оператора shot clock

На этапе MVP оператор shot clock одновременно: управляет таймером атаки через пульт хронометриста, подаёт сирену через штатный пульт табло 24/14, следит за игрой. Три параллельных задачи создают риск ошибки.

**Мера 1:** пульт хронометриста располагать рядом со штатным пультом табло, в зоне прямой досягаемости одного оператора.

**Мера 2:** в интерфейсе пульта визуально дублировать состояние shot clock крупным шрифтом с цветовой индикацией (зелёный > 10 с, жёлтый 5–10 с, красный < 5 с).

**Мера 3 (этап 2):** после реверс-инжиниринга, автоматическая сирена через программный комплекс, исключающая ручную подачу.

## 4.3 Программный комплекс

### 4.3.1 Общие требования

|     |     |
| --- | --- |
| **Параметр** | **Требование** |
| Тип | WEB GUI (Windows — обязательно; Linux, macOS — желательно) |

### 4.3.2 Модуль «Команды»

**Поля:** название, логотип (изображение), город. Без логотипа - заглушка.

**Операции:** CRUD, просмотр списка.

### 4.3.3 Модуль «Игроки»

Хранятся отдельно от команд (нормализация: исключение дублирования при переходе).

**Поля:** фамилия, имя, отчество, фото, игровой номер, привязка к команде.

**Операции:** CRUD, поиск, привязка/отвязка.

### 4.3.4 Модуль «Матчи»

**Создание:** выбор двух команд, длительность четверти (по умолчанию 10 мин), дата/время с часовым поясом, игровой день и площадка.

**Описание:** автоматически: «ДД.ММ.ГГГГ ЧЧ:ММ (ЧЧ:ММ мск), Город, Площадка».

**Состояния:** запланирован → разминка → в процессе (четверти 1‑4) → овертайм → завершён.

### 4.3.5 Модуль «Турниры / Игровой день»

На турнирах АСБ проводится 3‑5 матчей в день с интервалом 15–20 минут. Система поддерживает:

- **Игровой день:** группировка матчей по дате и площадке. Быстрое переключение между матчами без пересоздания.
- **Шаблон дня:** создание нескольких матчей заранее с предзаполненными командами и расписанием.
- **Быстрый старт:** переход к следующему запланированному матчу одной командой из панели управления.

Матч получает площадку через игровой день. Для одиночного матча без заранее подготовленного расписания система создаёт игровой день автоматически.

### 4.3.6 Время развёртывания

Время от включения сервера до готовности к проведению матча — не более 5 минут. Состав операций:

1.  Запуск ОС и автозапуск серверных сервисов (docker-compose up или системный сервис).
2.  Автозапуск клиентского приложения.
3.  Выбор матча из списка запланированных или быстрое создание нового.
4.  Подключение проводных пультов (USB hot-plug).

**Обоснование:** на турнирах между играми 15–20 минут. Развёртывание > 5 минут создаёт операционный риск.

## 4.9 Надёжность и отказоустойчивость

### 4.9.1 Raspberry — единственная точка отказа

Сервер на Raspberry, единственный узел, на котором работает серверная и клиентская части Комплекса. При его отказе (зависание, отключение питания) управление матчем через Комплекс невозможно.

**Меры снижения риска:**

**1\.** Непрерывное питание: сервер работает от встроенного аккумулятора + подключён к розетке. Заряд перед матчем не менее 80%.

**2\.** Автосохранение: состояние матча записывается в СУБД не реже 1 раза в секунду. Критические события (очки, фолы, старт/стоп) — синхронно.

**3\.** Быстрое восстановление: при перезапуске приложение восстанавливает состояние матча из СУБД за <5 с.

**4\.** Резерв: штатный проводной пульт табло 24/14 с продолжает работать независимо. Оператор ведёт shot clock и сирену без Комплекса.

**5\.** Регламент: в руководстве оператора описать порядок действий при отказе сервера (ручной протокол, бумажный scoresheet, продолжение через штатный пульт).

# 5 Реверс-инжиниринг табло 24/14 с

## 5.1 Постановка задачи

Табло 24/14 с (glashatay-tablo.ru) управляется проводным пультом через кабель 30 м. Документация на протокол отсутствует. Для программного управления необходим реверс-инжиниринг.

## 5.2 Состав работ

**1\.** Анализ разъёмов и электрических характеристик кабеля.

**2\.** Перехват и запись сигналов (логический анализатор, осциллограф).

**3\.** Декодирование протокола: формат пакетов, команды.

**4\.** Разработка аппаратного адаптера (USB протокол табло).

**5\.** Тестирование: верификация всех функций.

## 5.3 Критерий остановки

Реверс-инжиниринг может быть невозможен если:

- протокол проприетарный с шифрованием;
- интерфейс аналоговый (не цифровой), без дискретных команд;
- трудозатраты на декодирование превышают экономическую целесообразность.

**Критерий «стоп»:** если за 40 рабочих часов не удаётся декодировать базовые команды (старт, стоп, сброс 24, сброс 14, сирена) — этап признаётся нецелесообразным.

## 5.4 Альтернативный план

При невозможности реверс-инжиниринга:

**Вариант А:** замена физического табло 24/14 с на программное отображение shot clock исключительно на LED-экране. Физическое табло выводится из эксплуатации.

**Вариант Б:** параллельная работа: программный shot clock на LED, физическое табло управляется штатным пультом вручную. Десинхронизация — ответственность оператора.

**Вариант В:** замена табло 24/14 с на оборудование с документированным протоколом.

## 5.5 Десинхронизация физического табло и LED-экрана

До завершения реверс-инжиниринга (или при выборе варианта Б) существуют два независимых источника отображения shot clock: физическое табло 24/14 с (штатный пульт) и программный таймер на LED-экране. Расхождение неизбежно.

**6.3.3 Приоритет устойчивости состояния**

**6.5.1 Общие требования к LED-экранам**

- иметь безопасные зоны отступов по краям;
- учитывать возможную потерю части пикселей по краям LED-поля.

**6.5.1.2 Общие требования к данным**

Публичный экран должен обновляться только на основе подтверждённого сервером состояния.  
Запрещено:

- локально “дорисовывать” время;
- рассчитывать счёт на клиенте независимо от сервера;
- показывать неподтверждённые промежуточные состояния.

**6\. 5.2 Экран табло — режим “Игра”**

Это основной экран комплекса во время матча.

**6.5.2.1 Назначение**

Отображение всей критически важной игровой информации в режиме реального времени для зрителей, команд и судейского стола.

**6.5.2.2 Обязательные области интерфейса**

**A. Верхняя служебная зона**

Содержит:

- название матча или краткое описание;
- стадию матча;
- четверть / OT.

На MVP эта зона должна быть лаконичной. Запрещено перегружать её второстепенными подписями.

**B. Левая зона команды A**

Содержит:

- логотип команды;
- краткое или полное название команды;
- счёт команды;
- командные фолы;
- тайм-ауты;
- статистику игроков команды.

**C. Правая зона команды B**

Содержит:

- логотип команды;
- краткое или полное название команды;
- счёт команды;
- командные фолы;
- тайм-ауты;
- статистику игроков команды.

**D. Центральная зона**

Содержит:

- Game Clock;
- Shot Clock;
- индикатор владения;
- статус времени;
- при необходимости техническую индикацию режима.

**6.5.2.3 Иерархия важности элементов**

Приоритет визуальной значимости:

1.  счёт;
2.  игровое время;
3.  таймер атаки;
4.  четверть;
5.  владение;
6.  фолы/тайм-ауты;
7.  статистика игроков;
8.  служебные подписи.

Это означает, что статистика игроков должна быть на экране, но **не ценой ухудшения читаемости счёта и времени**.

**6.5.2.4 Отображение счёта**

Счёт — самый крупный элемент по обеим сторонам экрана.

Требования:

- минимум 3 знака на команду;
- моноширинное или визуально устойчивое отображение;
- отсутствие “скачков” ширины;
- визуальное выравнивание по базовой линии;
- недопустим мелкий счёт ради декоративных элементов.

**6.5.2.5 Отображение Game Clock**

Форматы:

- основной режим: мм:сс;
- последняя минута четверти / овертайма: сс.д.

Требования:

- таймер всегда расположен в визуальном центре внимания;
- формат переключается автоматически;
- запрещены анимированные смены формата;
- при остановке времени должно быть очевидно, что таймер не идёт.

**6.5.2.6 Отображение Shot Clock**

Форматы:

- обычный режим: 24, 23, ...;
- последние 5 секунд: 4.9, 4.8 и т.д.

Требования:

- цвет shot clock должен быть визуально отделён от Game Clock;
- элемент должен легко считываться без путаницы с основным временем;
- при скрытии/остановке shot clock состояние должно быть однозначным.

**6.5.2.7 Отображение владения**

Индикатор владения отображается как явная стрелка в сторону активной команды.

Требования:

- не должен теряться на фоне;
- не должен быть единственным цветовым индикатором без формы;
- при смене владения запрещены длинные анимации.

**6.5.2.8 Отображение командных фолов и тайм-аутов**

Для каждой команды должны отображаться:

- командные фолы текущей четверти;
- оставшиеся тайм-ауты.

Penalty state должен быть заметен, но не должен визуально перекрывать счёт.

**6.5.2.9 Отображение статистики игроков на LED**

Пользователь подтвердил, что на MVP статистика игроков на экран нужна.

Критически важное ограничение: LED-экран не должен превращаться в “таблицу протокола”. Поэтому статистика игроков на MVP должна быть **облегчённой и дисциплинированной по объёму**.

Рекомендуемый состав:

- номер игрока;
- фамилия или фамилия + инициал;
- очки;
- фолы.

**Требования к статистике игроков**

- выводится для каждой команды;
- отображаются только игроки заявки текущего матча;
- допускается ограничение по количеству строк, если экранная площадь ограничена;
- при нехватке места допускается сокращение имени;
- запрещён мелкий шрифт, который невозможно читать из зала;
- статистика не должна сдвигать счёт и таймер из основных областей.

**MVP-ограничение**

Если экранная плотность данных не позволяет одновременно качественно показать:

- счёт,
- время,
- shot clock,
- фолы/тайм-ауты,
- полную статистику всех игроков,

то в MVP допустимо предусмотреть один из вариантов:

1.  показывать весь состав, но в очень компактном виде;
2.  показывать ограниченное число игроков с прокруткой/пагинацией;
3.  показывать только активную пятёрку или список лидеров.

Этот момент должен быть заранее зафиксирован в UI-спецификации подрядчика, иначе здесь высокий риск “скрытой потери объёма”.

**6.5.2.10 Состояния режима “Игра”**

Экран должен корректно отображать следующие подрежимы:

- игра идёт;
- игра остановлена;
- тайм-аут;
- окончание четверти;
- техническая пауза;
- подтверждённая потеря соединения с сервером;
- отсутствие активного матча.

**6.5.3 Экран табло — режим “Перерыв”**

**6.5.3.1 Назначение**

Отображение состояния матча между четвертями и между половинами.

**6.5.3.2 Состав данных**

- текущий счёт;
- таймер перерыва;
- номер следующей четверти;
- счёт по четвертям;
- названия и логотипы команд;
- при наличии места — краткая статистика игроков.

**6.5.3.3 Требования**

- экран должен отличаться от режима “Игра” визуально, но сохранять узнаваемость;
- таймер перерыва — главный элемент;
- не допускается случайный показ игрового shot clock в этом режиме, если он не релевантен.

**6.5.4 Экран табло — режим “Разминка / До начала матча”**

**6.5.4.1 Назначение**

Используется до старта матча.

**6.5.4.2 Состав данных**

- логотипы команд;
- названия команд;
- дата/время матча;
- площадка;
- таймер обратного отсчёта до старта;
- статус “разминка” / “до начала матча”.

**6.5.4.3 Требования**

- экран должен быть визуально спокойным;
- в MVP не используются анимации выхода команд, заставки и видео;
- не допускается пустой чёрный экран при наличии запланированного матча.

**6.5.5 Экран табло — режим “Представление составов”**

**6.5.5.1 Назначение**

Режим предматчевого отображения составов команд.

**6.5.5.2 Состав данных**

Для каждой команды:

- логотип;
- название;
- список игроков;
- номер;
- фамилия;
- при наличии — фото.

**6.5.5.3 Ограничения MVP**

Без анимаций, без видеопереходов, без спонсорских блоков.

**6.5.6 Экран табло — режим “Тест / Проверка оборудования”**

**6.5.6.1 Назначение**

Служебный режим для:

- проверки контрастности;
- проверки цвета;
- проверки вёрстки;
- проверки отображения всех блоков перед матчем.

**6.5.6.2 Состав**

- тестовые значения счёта;
- тестовые таймеры;
- тестовые логотипы;
- цветовые поля;
- индикаторы сетки/безопасных зон по необходимости.

**6.5.6.3 Требования**

Это отдельный служебный экран, а не “пасхалка”. Он обязателен, так как в реальной эксплуатации нужен быстрый прогон перед матчем.

**6.5.7 Экран табло — “Служебная заглушка / Нет активного матча”**

**6.5.7.1 Назначение**

Показывается, если матч не выбран или ещё не запущен.

**6.5.7.2 Содержимое**

- логотип системы или площадки;
- текст “Матч не выбран” / “Ожидание запуска”;
- при наличии ближайшего матча — его анонс.

**6.5.7.3 Требования**

Недопустимы:

- пустой белый/чёрный экран;
- технические ошибки браузера;
- URL, служебные ошибки и stack trace.

**6.6. Операторские экраны**

**6.6.1 Главная панель матча**

Это главный рабочий экран оператора.

**6.6.1.1 Назначение**

Единая точка оперативного управления матчем.

**6.6.1.2 Обязательные блоки**

**A. Блок статуса матча**

Содержит:

- команды;
- текущую четверть;
- стадию матча;
- дату/время;
- площадку;
- статус матча.

**B. Блок управления временем**

Содержит:

- старт/стоп game clock;
- коррекцию времени;
- переключение четверти;
- таймер перерыва;
- таймер тайм-аута;
- shot clock: старт, стоп, 24, 14, скрыть/сброс.

**C. Блок управления счётом**

Содержит:

- быстрые действия по очкам;
- коррекцию командного счёта;
- переключение владения;
- тайм-ауты;
- фолы.

**D. Блок состава и статистики**

Содержит:

- игроков обеих команд;
- номер;
- фолы;
- очки;
- выделение выбранного игрока.

**E. Блок системных индикаторов**

Содержит:

- соединение с сервером;
- соединение с LED-экраном;
- соединение с пультом времени;
- соединение с пультом счёта;
- индикатор “LED-экран не проверен”.

**F. Журнал событий**

Показывает последние действия:

- кто набрал очки;
- какой фол зафиксирован;
- какой тайм-аут выдан;
- изменение времени;
- коррекцию счёта.

**6.6.1.3 Критическое UX-требование**

Главная панель не должна требовать переходов по вкладкам для выполнения частых действий матча. Всё критичное должно быть доступно с одного экрана или в один клик.

**6.6.1.4 Ошибки проектирования, которые нельзя допускать**

- маленькие кнопки управления временем;
- модальные окна на каждое действие;
- разнесение game clock и shot clock по разным экранам;
- необходимость искать игрока в длинном списке без фильтра;
- сложная навигация в момент игры.

**6.6.2 Экран быстрого выбора матча**

**6.6.2.1 Назначение**

Быстрый запуск одного из заранее подготовленных матчей.

**6.6.2.2 Содержимое**

- список ближайших матчей;
- дата/время;

**6.6.3 Экран игрового дня**

**6.6.3.1 Назначение**

Работа с серией матчей одного дня.

**6.6.3.2 Содержимое**

**6.6.5 Экран карточки команды**

**6.6.10 Экран настройки табло / профилей оформления**

**6.6.10.1 Назначение**

Настройка визуального оформления LED-табло без изменения кода.

**6.6.10.2 Настраиваемые сущности**

- профиль оформления;

- цвет shot clock;
- цвет фолов;

- цвета командных блоков.

**Типографика**

- основной шрифт интерфейса;
- шрифт цифровых значений;
- размеры для:
    - счёта,
    - времени,
    - shot clock,
    - статистики игроков,
    - служебных заголовков.

**Компоновка**

- включение/выключение статистики;
- количество отображаемых строк игроков;

**Контентные настройки**

- короткое/полное имя команды;
- формат имени игрока;
- формат отображения четверти;
- вид пустых значений;
- заглушка отсутствующего логотипа.

**6.6.10.4 Что считать кастомизацией, а что нет**

Кастомизация — это:

- параметры визуального оформления;
- параметры состава отображаемых данных;
- выбор профиля.

Кастомизация — это не:

- ручная правка CSS разработчиком;
- изменение кода;
- изменение структуры базы данных;
- настройка через конфиги, непонятные оператору, без UI.

Если на этапе MVP часть настройки всё же делается через конфигурационный файл, это должно быть отдельно зафиксировано и не называться “полноценной кастомизацией”.

**6.6.12.1 Назначение**

Появляется после рестарта приложения при наличии незавершённого матча.

**6.6.13 Экран подтверждения критических действий**

**6.6.13.1 Для чего нужен**

Подтверждения нужны только для реально опасных действий:

- сброс матча;
- завершение матча;
- удаление команды/игрока/матча;
- ручная коррекция времени на крупную величину;
- выход из активного матча.

**6.6.13.2 Что нельзя подтверждать модалками**

Нельзя требовать подтверждения для:

- начисления очков;
- фиксации фола;
- сброса 24/14;
- переключения владения.

Иначе интерфейс станет непригодным для матча в реальном темпе.

**6.6.14 Экран пустых состояний**

Во всех списках и служебных разделах должны быть продуманные пустые состояния:

- нет команд;
- нет игроков;
- нет матчей;
- нет активного игрового дня;
- нет доступных профилей;
- нет соединения с пультом.

Пустое состояние должно объяснять:

- что произошло;
- что делать дальше.

**6.7. Пульты**

**6.7.1 Пульт хронометриста**

**6.7.1.1 Назначение**

Быстрое управление временем матча и shot clock.

**6.7.1.2 Элементы**

- крупная индикация Game Clock;
- крупная индикация Shot Clock;
- кнопка старт/стоп;
- кнопка 24;
- кнопка 14;
- кнопка остановки shot clock;
- кнопки коррекции времени;
- переключение четверти;
- запуск тайм-аута.

**6.7.1.3 UX-требования**

- максимальный приоритет крупных кнопок;
- пригодность для сенсорного ввода;
- отсутствие мелких контролов;
- визуальная цветовая индикация состояния shot clock: зелёный / жёлтый / красный.

**6.7.2 Пульт оператора счёта**

**6.7.2.1 Назначение**

Ввод очков, фолов, тайм-аутов и управления владением.

**6.7.2.2 Элементы**

- выбор команды;
- выбор игрока;
- +1 / +2 / +3 / -1;
- фол +1 / -1;
- тайм-аут команды A/B;
- владение;
- ручная коррекция.

**6.7.2.3 UX-требования**

- не более одного промежуточного шага между выбором игрока и начислением очков;
- должна быть видна текущая выбранная команда/игрок;
- интерфейс должен снижать вероятность начислить очки не тому игроку.

**6.8. Кастомизация интерфейсов**

**6.8.1 Общий принцип**

Кастомизация в MVP должна быть ограниченной, но реальной.  
То есть оператор или администратор должны иметь возможность менять оформление без привлечения разработчика.

**6.8.2 Состав кастомизации MVP**

**6.8.2.1 Обязательная кастомизация**

1.  Цвета основных элементов
2.  Логотипы команд
3.  Фон табло
4.  Шрифты
5.  Размеры ключевых блоков
6.  Включение/выключение отдельных блоков
7.  Формат отображения статистики игроков
8.  Сохранение в профиль

**6.8.2.2 Не входит в MVP**

1.  Анимации
2.  Видеофоны
3.  Рекламные блоки
4.  Спонсорские врезки
5.  Overlay для стрима
6.  Конструктор с произвольным drag-and-drop уровнем Figma
7.  Посценарная режиссура экранов

**6.8.3 Профили оформления**

Профиль должен включать:

- название;
- набор цветов;
- шрифты;
- layout preset;
- правила отображения статистики;
- фоновую настройку;
- настройки названий и сокращений.

Профили применяются:

- к матчу;
- к площадке;
- вручную оператором.

**6.8.4 Требования к качеству кастомизации**

Кастомизация считается реализованной только если:

- изменение видно без перезапуска всей системы;
- профиль можно сохранить и повторно применить;
- существует дефолтный профиль;
- при ошибке в пользовательских настройках остаётся безопасный резервный профиль;
- логотипы и цвета не ломают layout.

**6.9. Критические ограничения и риски frontend-реализации**

**9.1 Риск перегрузки LED-экрана**

Так как на экран дополнительно выводится статистика игроков, существует риск перегрузить основное табло.

Требование:  
до начала разработки подрядчик обязан согласовать один конкретный wireframe игрового табло, а не абстрактное “будет красиво и удобно”.

**6.9.2 Риск фальшивой кастомизации**

Очень частая проблема: подрядчик пишет “кастомизация есть”, но фактически это:

- 2–3 жёстко зашитые темы;
- правка JSON руками;
- переключение пары цветов.

Нужно прямо фиксировать, что кастомизация — это отдельный UI-экран с сохраняемыми профилями.

**6.9.3 Риск раздробления операторского UX**

Если управление временем, счётом и игроками будет раскидано по вкладкам, оператор начнёт ошибаться.

Следовательно:  
все матчевые действия должны быть либо на одном экране, либо в одном уровне вложенности.

**6.9.4 Риск недооценки служебных экранов**

Служебные экраны часто “забывают” в оценке:

- тестовый экран;
- диагностика;
- восстановление после сбоя;
- пустые состояния;
- подтверждения критических действий.

Но именно они обычно всплывают на приёмке и начинают раздувать сроки. Их нужно считать частью MVP frontend.

**6.10. Минимальный состав frontend deliverables по экранам**

Frontend-часть по MVP не может считаться выполненной без следующего набора:

1.  LED-табло:
    - игра;
    - перерыв;
    - разминка;
    - представление составов;
    - тест;
    - заглушка без матча.
2.  Операторские экраны:
    - главная панель матча;
    - выбор матча;
    - игровой день;
    - команды;
    - карточка команды;
    - игроки;
    - карточка игрока;
    - матчи;
    - карточка матча;
    - настройки табло;
    - системный статус;
    - восстановление после сбоя;
    - подтверждения критических действий;
    - пустые состояния.
3.  Пульты:
    - пульт хронометриста;
    - пульт оператора счёта.

**6.11. Формулировка для приёмки frontend-части**

Frontend-часть считается выполненной, если:

- реализованы все перечисленные экраны;
- реализованы все обязательные состояния экранов;
- LED-экран работает в полноэкранном режиме;
- операторский контур позволяет провести матч без обращения к разработчику;
- пульты пригодны для работы в реальном темпе;
- служебные экраны диагностики и восстановления присутствуют;
- кастомизация доступна через UI и сохраняется в профили;
- статистика игроков отображается на табло без потери читаемости ключевых элементов;
- пустые и аварийные состояния обработаны;
- экранная логика не противоречит требованиям матча и роли операторов.

# 7 Требования к процессу разработки

## 7.1 Управление исходным кодом

Git. Хостинг определяется разработкой. Обязательно:

- ветвление: master, develop

## 7.2 Контейнеризация

Серверные компоненты (API-сервер, СУБД, веб-сервер пультов) в Docker. Развёртывание docker-compose.

**Обоснование Docker:** обеспечивает воспроизводимость среды на любом устройстве. Исключает проблему «работает на моей машине». Упрощает установку: оператору не нужно ставить СУБД, зависимости вручную.

Клиентская часть (десктоп с GUI) — нативно, так как требует доступ к дисплею и HDMI.

|     |     |
| --- | --- |
| **Сервис** | **Назначение** |
| api | API-сервер (бизнес-логика, WebSocket, high-res timer) |
| db  | Реляционная СУБД |
| web-remotes | Веб-сервер программных пультов |

## 7.3 CI/CD

Автоматический пайплайн при push/merge request. Инструмент на этапе разработки требуется только для удобства разработки и является **опциональным компонентом системы**.

## 7.4 Тестирование

|     |     |     |
| --- | --- | --- |
| **Уровень** | **Область** | **Примеры** |
| Unit | Бизнес-логика | Таймеры, валидация FIBA, расчёт счёта |
| Integration | API + СУБД | CRUD, WebSocket-события, транзакции |

E2E и нагрузочное — определяется разработкой.

## 7.5 Документация

|     |     |
| --- | --- |
| **Документ** | **Содержание** |
| README.md | Архитектура, развёртывание (docker-compose up), конфигурация |
| API-документация | Эндпоинты, WebSocket, форматы данных (Swagger/OpenAPI) |
| Комментирование кода | JSDoc/TSDoc или аналог для публичных модулей |
| Руководство оператора | Работа с приложением, пультами, проведение матча, действия при сбоях, настройка яркости VP410 |
| Руководство администратора | Установка, настройка, резервное копирование, обновление |

## 7.6 Обучение операторов

Сертификация не требуется. Обучение:

**1\.** Персональное обучение от разработчика при вводе системы в эксплуатацию.

**2\.** Руководство оператора (п. 6.5) печатная и электронная версии.

**Требование к UX:** интерфейс приложения и пультов должен быть достаточно очевиден, чтобы новый оператор (студент-волонтёр) разобрался в основных функциях за 5 минут без дополнительного обучения.

# 10 Риски и ограничения

|     |     |     |     |     |
| --- | --- | --- | --- | --- |
| **№** | **Риск** | **Последствие** | **Вероятность** | **Мера** |
| 1   | Реверс-инжиниринг невозможен | Нет программного управления табло 24/14, нет автосирены | Средняя | Альтернативный план (п. 5.4): варианты А/Б/В. Критерий стоп: 40 ч. |
| 2   | Десинхрон shot clock (LED vs физ. табло) | Зрители видят разные значения. Протесты. | Высокая (до этапа 0) | Выбрать вариант из п. 5.5.1 до начала MVP. |
| 3   | Точность таймера при высокой нагрузке CPU | Дрейф game clock, неточные десятые доли | Низкая | Серверный high-res timer (п. 4.1.4). Тестирование при нагрузке. |
| 4   | Отказ Raspberry Pi в ходе матча | Полная остановка Комплекса | Низкая | Меры п. 4.9.1. Аккумулятор ≥ 80%. Регламент ручного продолжения. |
| 5   | Системные уведомления Windows поверх табло | Зрители видят уведомление ОС вместо счёта | Средняя | Полноэкранный режим + подавление уведомлений (п. 4.1.5). Тестирование. |
| 6   | Повреждение СУБД при обесточивании | Потеря данных матча | Низкая | ACID-совместимая СУБД, WAL. Резервное копирование перед матчем (п. 4.8.1). |
| 7   | VP410 зависание без обратной связи | LED показывает старый кадр, оператор не знает | Низкая | Визуальный контроль. Индикатор в панели (п. 4.1.6). |
| 8   | Когнитивная перегрузка оператора shot clock | Пропуск сирены, ошибка таймера | Средняя | Меры п. 4.2.1. Этап 2: автосирена. |
