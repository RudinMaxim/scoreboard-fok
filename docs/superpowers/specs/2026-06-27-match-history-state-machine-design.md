# Match History, Snapshots And State Machine Design

Дата: 2026-06-27

Статус: согласованный архитектурный дизайн

Область: MVP backend, операторские интерфейсы и Timer Service

## 1. Назначение

Документ описывает две связанные возможности:

1. Пошаговую отмену и повтор действий оператора через кнопки `Назад` и `Вперёд`.
2. Иерархические конечные автоматы, которые определяют допустимые состояния матча и переходы между ними.

Цель MVP - дать оператору безопасный способ исправлять последнее действие без удаления истории и не позволять системе выполнять команды, недопустимые в текущем состоянии матча.

Основания:

- `docs/data-model.md`;
- `docs/api-and-component-contracts.md`;
- `docs/timer-service-architecture.md`.

## 2. Принятые Решения

- `MATCH_EVENT` остаётся append-only журналом и источником аудита.
- После каждого подтверждённого действия оператора сохраняется полный снимок состояния матча.
- При подготовке матча сохраняется начальный снимок со значениями по умолчанию.
- Все поддержанные типы действий по умолчанию доступны для отмены. При реализации отдельные типы можно исключить из политики обратимости.
- `Undo` и `Redo` также являются действиями: они записываются в журнал и создают новые снимки.
- Существующие события и снимки никогда не редактируются и не удаляются.
- Официальная история матча линейная. Новое действие после `Undo` делает прежний путь `Redo` недоступным, но не удаляет его из аудита.
- При восстановлении снимка значения игрового времени и времени атаки восстанавливаются, но оба таймера остаются остановленными.
- Backend и domain layer являются единственным источником истины для переходов state machine. UI только отображает доступность команд.
- Периодические clock snapshots, heartbeat, отклонённые команды и повторы по idempotency key не считаются действиями оператора и не создают снимок истории.

## 3. Границы MVP

В MVP входят:

- начальный снимок при подготовке матча;
- полный снимок после каждого подтверждённого действия оператора;
- отмена одного действия за одно нажатие;
- повтор одного отменённого действия за одно нажатие;
- линейная политика ветвления;
- настройка типов обратимых действий через конфигурацию по умолчанию;
- backend guards на основе иерархической state machine;
- аудит отмен, повторов и отклонённых команд.

Не входят:

- выбор оператором произвольной ветки истории;
- параллельные официальные версии одного матча;
- редактирование или удаление событий;
- свободный переход к произвольной точке истории;
- аналитические ветки после матча;
- изменение политики обратимости во время активного матча.

## 4. Модель Истории

### 4.1 Источник истины

`MATCH_EVENT` хранит подтверждённые игровые факты и важные служебные изменения. Снимки ускоряют восстановление и дают стабильную точку для `Undo/Redo`, но не заменяют журнал событий.

Если снимки повреждены, состояние можно проверить и пересобрать из `MATCH_EVENT`. Если журнал и снимок расходятся, правильным считается результат воспроизведения журнала.

### 4.2 Действие оператора

Одно подтверждённое действие оператора имеет:

- `actionId`;
- `matchId`;
- монотонный `sequence`;
- `actionType`;
- `source` и `operatorId`;
- `clientCommandId` для идемпотентности;
- `stateVersionBefore`;
- `stateVersionAfter`;
- `snapshotBeforeId`;
- `snapshotAfterId`;
- признак `reversible`;
- ссылку на созданный `MATCH_EVENT`;
- `causationActionId` для `Undo/Redo`;
- timestamp.

Отклонённая команда записывается в `COMMAND_LOG`, но не создаёт `MATCH_EVENT` и снимок состояния.

Навигационные события `history_undo` и `history_redo` входят в аудит, но не становятся целями следующего `Undo`. Для навигации backend отдельно хранит стек активных действий и стек доступного `Redo`.

### 4.3 Снимок состояния

Новая проекция `MATCH_STATE_SNAPSHOT` создаётся:

1. При подготовке матча как снимок с `sequence = 0`.
2. После каждого подтверждённого действия оператора.
3. После каждого подтверждённого `Undo` или `Redo`.

Снимок содержит полный бизнес-контекст, необходимый операторским экранам и восстановлению:

- статус матча и state machine state;
- текущий период;
- счёт команд и счёт по периодам;
- персональные очки и фолы игроков;
- командные фолы и тайм-ауты;
- владение, если оно используется в операторском контуре;
- игровое время и время атаки;
- признаки `running` для обоих таймеров;
- display mode;
- `stateVersion` и `timerVersion`;
- версию политики обратимости.

Хранится один полный снимок `after` для каждого действия. Состояние `before` определяется ссылкой на предыдущий снимок, поэтому одинаковое состояние не дублируется дважды в одной записи действия.

Снимки являются immutable. Текущий официальный снимок определяется указателем матча `currentSnapshotId`.

### 4.4 Политика обратимости

В системной конфигурации хранится список `reversibleActionTypes`. При подготовке матча он копируется в неизменяемую `MATCH_HISTORY_POLICY` этого матча.

Начальная MVP-политика включает все реализованные операторские действия. Во время реализации из списка можно убрать действия, для которых ещё нет безопасного восстановления и полного набора тестов.

Изменение глобального значения влияет только на матчи, подготовленные после изменения. Активный матч продолжает использовать собственную зафиксированную политику.

## 5. Undo И Redo

### 5.1 Undo

Кнопка `Назад` отменяет последнее подтверждённое действие, которое находится в текущей официальной линии истории и разрешено политикой матча.

Backend выполняет изменение бизнес-состояния в одной транзакции БД:

1. Проверяет `expectedStateVersion`, роль оператора и state machine guard.
2. Проверяет, что целевое действие обратимо и ещё не отменено.
3. Загружает связанный снимок `before`.
4. Формирует восстановленное состояние.
5. Принудительно устанавливает `gameClock.running = false` и `shotClock.running = false`.
6. Создаёт событие `history_undo` с `reverted_event_id` и `causationActionId`.
7. Обновляет производные агрегаты и `MATCH_CLOCK_STATE`.
8. Создаёт новый полный `MATCH_STATE_SNAPSHOT`.
9. Увеличивает `stateVersion`, фиксирует транзакцию и создаёт outbox-задание синхронизации Timer Service.

После commit backend синхронизирует остановленный clock snapshot с Timer Service. Обычный успешный ответ и публикация рабочего snapshot выполняются после подтверждения Timer Service. БД и Timer Service не считаются одной распределённой транзакцией.

Если последнее действие запрещено к отмене, кнопка `Назад` отключена и API возвращает причину. MVP не перепрыгивает через необратимое действие, потому что восстановление более раннего полного снимка могло бы неявно отменить это действие.

### 5.2 Redo

Кнопка `Вперёд` повторно применяет последнее отменённое действие из текущей линии истории.

Backend выполняет те же проверки версии, роли и state machine. Результат записывается как новое событие `history_redo` и новый снимок. Исходное событие не активируется редактированием.

После `Redo` таймеры также остаются остановленными. Оператор запускает их отдельной командой.

Последовательные нажатия `Назад` добавляют действия в стек `Redo`. Последовательные нажатия `Вперёд` применяют их в обратном порядке. События самих команд `Undo/Redo` при этом пропускаются.

### 5.3 Линейное ветвление

После `Undo` система хранит ссылку на доступное действие для `Redo`. Если до `Redo` оператор выполняет новое действие:

- новая команда продолжает официальную линию истории;
- прежний `Redo` становится недоступен;
- весь стек `Redo` закрывается для оперативной навигации;
- старое действие, его отмена и снимки остаются в журнале;
- UI показывает, что путь повтора был закрыт новым действием.

Оператор не выбирает ветки и не может переключить официальный матч на старую ветку.

## 6. State Machine

### 6.1 Ответственность

State machine находится в `libs/domain` и используется backend перед выполнением команды. Она принимает текущее состояние и команду, проверяет guards и возвращает допустимый переход либо доменную ошибку.

Frontend может использовать тот же read model для disabled-состояний кнопок, но backend повторно проверяет каждую команду. Timer Service управляет точным ходом счётчиков и `timerVersion`, но не принимает бизнес-решения о периодах, счёте или допустимости `Undo/Redo`.

### 6.2 Иерархия состояния матча

Корневые состояния:

- `draft`;
- `prepared`;
- `active`;
- `recovery`;
- `finished`;
- `archived`.

Внутри `active`:

- `pre_period`;
- `in_period`;
- `break`.

Внутри `in_period` работают независимые регионы:

- game clock: `stopped`, `running`, `expired`;
- shot clock: `idle`, `stopped`, `running`, `expired`.

Независимые регионы не превращаются в одно перечисление комбинаций. Например, `gameClock.running` и `shotClock.stopped` являются двумя параллельными состояниями, а не отдельным корневым статусом.

### 6.3 Основные переходы

- `draft -> prepared`: матч валиден, команды и составы готовы, создан начальный снимок.
- `prepared -> active.pre_period`: оператор начинает проведение матча.
- `active.pre_period -> active.in_period`: начинается период.
- `active.in_period -> active.break`: период завершён, таймеры остановлены.
- `active.break -> active.in_period`: начинается следующий период.
- `active.*|finished -> recovery`: подтверждённая ошибка восстановления или рассинхронизация.
- `recovery -> active.pre_period|active.in_period|active.break|finished`: синхронизация завершена, оператор подтвердил восстановленный снимок.
- `active -> finished`: матч завершён явной командой.
- `finished -> archived`: матч закрыт для оперативных изменений.

### 6.4 Guards

Минимальные guards MVP:

- старт игрового времени разрешён только в `active.in_period`;
- старт времени атаки разрешён только в `active.in_period` и при допустимом game clock state;
- завершение периода требует остановленных таймеров либо явного подтверждённого override;
- изменение счёта, фолов и тайм-аутов запрещено в `draft`, `finished` и `archived`;
- переход к следующему периоду запрещён, если текущий период не завершён;
- `Undo/Redo` запрещены в `archived`;
- `Undo/Redo` требуют совпадения `stateVersion` и политики обратимости;
- state machine проверяет не только текущий state, но и state из восстанавливаемого снимка;
- восстановление clock snapshot всегда переводит оба таймера в `stopped`;
- во время `recovery` обычные игровые команды блокируются.

## 7. API И UI

### 7.1 Команды

MVP добавляет:

- `POST /api/v1/matches/{matchId}/history/undo`;
- `POST /api/v1/matches/{matchId}/history/redo`.

Команда содержит `clientCommandId` и `expectedStateVersion`. Целевое действие выбирает backend, чтобы клиент не мог произвольно восстановить старое состояние.

Ответ содержит:

- `actionId`;
- `eventId`;
- новый `stateVersion`;
- новый `snapshot`;
- `history.canUndo`;
- `history.canRedo`;
- краткое описание следующего доступного действия.

### 7.2 Операторский интерфейс

На панели матча доступны две icon buttons:

- стрелка назад: отменить последнее действие;
- стрелка вперёд: повторить отменённое действие.

Кнопки имеют tooltip с типом и временем действия. Disabled-состояние сопровождается причиной, доступной оператору. После подтверждения UI применяет только snapshot backend и не вычисляет отмену локально.

После `Undo/Redo` UI явно показывает, что таймеры остановлены. Запуск выполняется отдельной кнопкой `Старт`.

## 8. Ошибки И Конкурентность

Доменный API использует следующие ошибки:

- `409 STATE_VERSION_CONFLICT`: клиент отправил устаревшую версию;
- `409 REDO_BRANCH_INVALIDATED`: после `Undo` было выполнено новое действие;
- `422 ACTION_NOT_REVERSIBLE`: тип действия исключён политикой;
- `422 STATE_TRANSITION_NOT_ALLOWED`: команда запрещена текущим состоянием;
- `422 HISTORY_EMPTY`: нет действия для отмены или повтора;
- `503 TIMER_RESTORE_FAILED`: Timer Service не подтвердил восстановление clock snapshot.

Команды идемпотентны по `clientCommandId`. Повтор запроса возвращает прежний результат и не создаёт второй снимок или событие.

Если Timer Service не подтвердил восстановление времени, зафиксированная операция получает `timerSyncStatus = pending`, матч переводится в `recovery`, а оператор получает экран восстановления. Outbox повторяет идемпотентную команду `/restore`. Повтор `Undo/Redo` с тем же `clientCommandId` продолжает эту операцию и не создаёт новый снимок.

После подтверждения Timer Service операция получает `timerSyncStatus = confirmed`, backend публикует рабочий snapshot и завершает исходную команду. Пока синхронизация не подтверждена, новые игровые команды запрещены.

## 9. Тестирование

### 9.1 Domain tests

- каждый допустимый переход state machine;
- каждый запрещённый переход и guard;
- отмена и повтор для каждого включённого типа действия;
- запрет обычных игровых действий в `finished` и `archived`;
- остановка обоих таймеров после `Undo/Redo`;
- закрытие `Redo` после нового действия.

### 9.2 Persistence tests

- начальный снимок создаётся при подготовке матча;
- после каждого подтверждённого действия создаётся ровно один новый снимок;
- отклонённая и повторная идемпотентная команда не создаёт снимок;
- события и снимки immutable;
- `currentSnapshotId` обновляется в той же транзакции, что событие и агрегаты;
- агрегаты можно сверить с воспроизведением `MATCH_EVENT`.

### 9.3 Integration tests

- `Undo/Redo` с оптимистической конкуренцией;
- подтверждение восстановления времени Timer Service;
- переход в recovery при отказе Timer Service;
- повтор pending-синхронизации через outbox без второго события;
- WebSocket публикует новый snapshot только после commit;
- два оператора не могут одновременно отменить одно действие.

### 9.4 UI tests

- правильные disabled-состояния стрелок;
- tooltip показывает следующее действие;
- после новой команды кнопка `Вперёд` отключается;
- после восстановления оба таймера отображаются остановленными;
- конфликт версии приводит к full resync, а не к локальной коррекции.

## 10. Acceptance Criteria

Дизайн считается реализованным, если:

- у подготовленного матча есть начальный полный снимок;
- каждое подтверждённое действие оператора создаёт полный immutable snapshot;
- `Undo` и `Redo` не редактируют и не удаляют существующие события;
- новое действие после `Undo` закрывает путь `Redo`;
- восстановленные таймеры всегда остановлены;
- набор обратимых действий зафиксирован для матча при подготовке;
- backend отклоняет команды, недопустимые текущей state machine;
- история, агрегаты, outbox-задание и указатель текущего snapshot обновляются одной транзакцией БД;
- рабочий snapshot публикуется только после подтверждения остановленного времени Timer Service;
- все переходы, ошибки и конкурентные сценарии покрыты тестами.
