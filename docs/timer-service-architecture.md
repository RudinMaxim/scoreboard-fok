# Архитектурное решение: Timer Service и MCU-пульты

## Статус

Принято для дальнейшей проработки MVP и этапа 2.

## Техническое решение

Проект ограничивается двумя основными языками:

- Node.js - backend, бизнес-логика, FIBA-валидация, БД, WebSocket, UI-интеграция;
- C++ - низкоуровневый контур: будущий Timer Service и прошивка MCU-пультов.

Go для Timer Service не используется. Причины:

- MCU-прошивка практически неизбежно требует C/C++ из-за GPIO, USB/HID/Serial, debounce, watchdog и отладки с железом;
- отдельный Go-сервис добавлял бы третий технологический стек без достаточной пользы;
- Timer Service и MCU-прошивка относятся к одному low-level контуру, поэтому их лучше проектировать в одном языке и одной модели протоколов.

Timer Service должен оставаться простым runtime-сервисом счётчиков:

- generic-команды `start`, `stop`, `set`, `adjust`;
- monotonic clock;
- версионированный snapshot;
- без FIBA-правил;
- без БД;
- без знания игровых сценариев `24`, `14`, `timeout`, `period_change`.

Node.js backend интерпретирует игровые действия и преобразует их в generic-команды Timer Service.

## Контекст

В системе есть два типа времени:

- `game clock` - игровое время периода;
- `shot clock` - время атаки 24/14 с.

Таймеры должны останавливаться, запускаться, корректироваться и сбрасываться во время игры. Требование точности - не хуже +/-10 мс на 10 минут непрерывного отсчёта.

Node.js backend удобен для бизнес-логики, WebSocket, СУБД и UI, но не должен быть единственным механизмом точного хронометрирования через `setInterval` / `setTimeout`. Аппаратный MCU-пульт также не должен становиться точкой правды матча, потому что у него нет СУБД, журнала событий и полноценного восстановления.

## Решение

Основной поток:

```text
MCU / аппаратный пульт
  -> Node.js backend / input gateway
  -> Timer Service
  -> Node.js backend
  -> СУБД / WebSocket / UI
```

Для MVP программный пульт хронометриста обращается в Node.js backend. Node.js backend интерпретирует игровое действие, валидирует его и отправляет в Timer Service только generic-команды счётчиков.

## Ответственность компонентов

### MCU / аппаратный пульт

MCU является клиентом ввода-вывода, а не источником истины.

Обязанности:

- читать физические кнопки;
- выполнять debounce;
- отправлять события ввода в Node.js backend / input gateway;
- хранить локальный `seq` для идемпотентности команд;
- принимать подтверждённое состояние;
- показывать game clock и shot clock на локальном дисплее;
- контролировать heartbeat;
- показывать `NO LINK` при потере связи;
- использовать watchdog для самовосстановления прошивки.

MCU может локально интерполировать отображаемый обратный отсчёт между снимками состояния, но обязан корректироваться по подтверждённому состоянию Node.js backend.

MCU не должен:

- самостоятельно вести официальный матчевый таймер;
- принимать бизнес-решения по FIBA;
- записывать журнал матча;
- продолжать опасные действия при потере связи с серверной частью.

### Timer Service

C++ Timer Service является точкой правды значений счётчиков времени в активном процессе матча, но не содержит бизнес-логику матча.

Обязанности:

- использовать monotonic clock;
- хранить состояние именованных счётчиков, например `game_clock` и `shot_clock`;
- принимать только generic-команды `start`, `stop`, `set`, `adjust`;
- фиксировать monotonic timestamp получения команды;
- рассчитывать новое состояние без накопления ошибки интервалов;
- выдавать версионированный clock snapshot;
- возвращать рассчитанное состояние Node.js backend для записи и рассылки;
- принимать последний подтверждённый snapshot от Node.js backend после восстановления.

Timer Service не знает правил FIBA, не интерпретирует кнопки `24` / `14`, не управляет периодами и тайм-аутами, не хранит основную матчевую БД и не заменяет append-only журнал.

### Node.js backend

Node.js backend является точкой правды бизнес-состояния матча.

Обязанности:

- валидировать статус матча, период, ограничения FIBA, игроков и команды;
- принимать clock snapshots от Timer Service;
- записывать `MATCH_EVENT` и `MATCH_CLOCK_STATE`;
- обновлять счёт, фолы, тайм-ауты и производные агрегаты;
- рассылать подтверждённое состояние в UI и пульты;
- восстанавливать состояние из СУБД после сбоя;
- передавать восстановленный clock snapshot в Timer Service.

## Модель времени

Timer Service не уменьшает остаток времени накопительным циклом. Он хранит базовое состояние и timestamp запуска.

```text
baseRemainingMs
startedAtMonoNs
running
stateVersion
```

Текущее значение при запущенном таймере:

```text
remainingMs = baseRemainingMs - (nowMonoNs - startedAtMonoNs)
```

При `stop`, `set` и `adjust` сервис сначала материализует текущее значение, затем применяет команду и создаёт новую версию состояния.

## Команды

Timer Service принимает уже интерпретированные generic-команды. Например, игровое действие “сбросить shot clock на 14” преобразуется вне Timer Service в команду `set` для счётчика `shot_clock`.

Минимальный формат команды:

```json
{
  "commands": [
    {
      "counter": "shot_clock",
      "action": "set",
      "valueMs": 14000
    }
  ]
}
```

Минимальный ответ:

```json
{
  "version": 1842,
  "counters": {
    "game_clock": {
      "id": "game_clock",
      "remainingMs": 522300,
      "running": true
    },
    "shot_clock": {
      "id": "shot_clock",
      "remainingMs": 14000,
      "running": true
    }
  }
}
```

Идемпотентность команд уровня устройства (`deviceId + seq`) должна обеспечиваться на границе пульта или Node.js backend. Timer Service применяет полученный batch атомарно: если одна команда в batch некорректна, состояние не меняется частично.

## Подтверждение состояния

Официальным для UI и операторов считается состояние, подтверждённое серверной частью:

1. Timer Service получил команду и timestamp.
2. Timer Service рассчитал новое состояние времени.
3. Node.js backend проверил исходное игровое действие по бизнес-правилам.
4. Node.js backend записал событие и snapshot в СУБД.
5. Node.js backend разослал подтверждённое состояние.

Если Node.js backend отклоняет исходное игровое действие, он не должен отправлять его в Timer Service. Если рассинхронизация всё же возникла, Node.js backend применяет корректирующий snapshot.

## Отказы и восстановление

### Потеря связи MCU с Node.js backend

MCU показывает `NO LINK`, прекращает отправку опасных повторных команд и ждёт восстановления связи. Оператор использует панель оператора или штатный ручной режим.

### Перезапуск Timer Service

Node.js backend передаёт последний сохранённый `MATCH_CLOCK_STATE`. До получения snapshot команды времени блокируются.

### Перезапуск Node.js backend

Timer Service может продолжать хранить live-состояние времени, но официальная запись и рассылка возобновляются только после восстановления Node.js backend. После восстановления Node.js backend сверяет состояние с СУБД и отправляет Timer Service подтверждённый snapshot.

### Отключение Raspberry Pi

Система восстанавливается из СУБД: `MATCH_EVENT`, `MATCH_CLOCK_STATE`, `MATCH_TEAM_STATE`, `MATCH_TIMEOUT_BUCKET`, `MATCH_PLAYER_STAT`, `MATCH_PERIOD_SCORE`.

## MVP и этап 2

MVP:

- Timer Service как отдельный серверный процесс;
- программный пульт хронометриста;
- проводное подключение;
- API generic-команд счётчиков;
- запись clock events и snapshots через Node.js backend.

Этап 2:

- аппаратный MCU-пульт;
- корпус, PCB, физические кнопки;
- локальная индикация game clock и shot clock;
- USB/Ethernet-протокол событий ввода с Node.js backend;
- интеграция с адаптером табло 24/14 и автоматической сиреной при успешном реверс-инжиниринге.
